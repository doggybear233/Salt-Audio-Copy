# 提示（toast）重新设计 · 方案

## 现状是怎么来的

插件的所有提示都走同一行：

```kotlin
// ConfigActions.kt:64
private fun toast(msg: String, type: ToastType = ToastType.Success) {
    runCatching { WorkshopApi.ui.toast(msg, type) }
}
```

`WorkshopApi.ui.toast()` 是**宿主**画的通知：整宽、贴窗口底、圆角、带成功/警告/失败三种颜色。
全仓库约 40 处调用（扫描光驱、抓轨完成、导出 album.json、CD-TEXT 读取、错误……）。

问题不在颜色，在位置：宿主把它钉在窗口最底部，而我们把坞也放在底部，
于是「正在抓第 7 轨」的坞和「继续抓轨」的通知必然叠在一起——**插件改不了宿主的 toast 位置**，
只能选择「别用宿主 toast 说这类话」。

截图里的三条（绿/黄）就是宿主 toast：它盖住坞的进度条与路径行，还压住下面的播放条。

## 三个方案

### 方案 A · 坞上沿状态条（推荐）

通知画成一条和坞同宽、贴在坞紧上沿的条：

```
┌────────────────────────────────────────────────┐
│ √ 继续抓轨 · 第 12 轨 34%            4 秒后收起 │  ← 状态条
├────────────────────────────────────────────────┤
│ [封面] Def Tech — GREATEST HITS   [抓整盘][暂停] │  ← 坞
└────────────────────────────────────────────────┘
```

- 实现：`PanelState.notice` + `LaunchedEffect(notice) { delay(4000); clear }`，坞的 `Column` 里加一个可折叠的行。
- 优点：零遮挡、和坞同宽对齐、宿主和插件风格都能接受；面板收起时消息退回坞内的状态行。
- 缺点：只在面板可见时看得到（但面板本来就在 CD 工具箱页上）。
- 代码量：约 80 行，全在插件内，不依赖宿主 API。

### 方案 B · 右上方气泡

气泡贴在坞的右上角外侧，3 秒淡出，可点 × 立刻关，多条向上堆叠。

- 优点：离坞的按钮最远，视觉上「不打断」；适合「已导出 album.json」这类可回看的消息。
- 缺点：**受父容器裁剪限制**——我们只能在自己那块 composable 的范围内画，
  如果宿主给的高度只够坞，气泡就会被裁掉；要稳妥就得预留一块空白区域，坞会显得偏小。
- 代码量：约 100 行 + 需要给坞预留 `top padding`。

### 方案 C · 页面左上角通知

通知挪到页面左上角（离坞最远），用于「完成 / 失败」这类离开面板也要知道的消息。

- 优点：不打扰正在进行的操作。
- 缺点：同样受裁剪限制；而且它在页面里，用户切回「歌曲」页就看不到了，
  真要「离开也看到」只能是宿主级通知（也就是现在的 toast）或 Windows 通知。
- 代码量：约 60 行，但收益依赖宿主布局是否允许我们往上画。

## 建议

**A 为主体 + 失败仍走宿主 toast**：

| 消息类型 | 走哪 |
|---|---|
| 进行中/成功的例行消息（扫描完成、继续抓轨、已导出、CD-TEXT 读到 N 轨） | 方案 A 的状态条 |
| 失败/需要用户处理（无光驱、不是音频 CD、SCSI 错误、文件占用） | 宿主 toast（保证即使坞被折叠也能看见） |

理由：例行消息量大、位置敏感；失败消息量小、可见性优先。
这也把 40 处调用分成两类，改动可以只改 `toast()` 一个函数 + 加 `Notify.fail()`。

## 待你定

1. 选 A / B / C（或 A+B 混用：成功走 A、可回看的走 B）。
2. 状态条停留时长：3 秒 / 4 秒 / 不自动消失（手动关）。
3. 失败消息是否也改成状态条（我建议保留宿主 toast）。

`F1-设置面板-双主题.png` 是对应的排版重做，解决你截图里「又粗又细、留白太多」：
